# Rust 原生引擎：10 万文件实测（v1 历史记录）

新版 v2 的同机前后对照见 [块级索引](chunk-index.md)，不要与本报告跨机器混算。

## 测试范围

- 本机 Linux 4.4.302+，x86_64，8 个逻辑 CPU；release 构建。
- 独立临时目录，10 万个空文件、1000 个子目录，两引擎使用同一组路径；未修改用户索引。
- 两套索引全部建好后才测查询；交替切换引擎顺序，减少先后测量的偏差。
- 每种查询记录首次样本，预热 3 次，再统计 20 次的 P50/P95。所有样本（含预热）校验结果。
- 不清空系统缓存，不承诺冷缓存。耗时包含 CLI 启动、可选 GNU time 包装和输出到临时文件；建库/更新含统计缓存维护。
- 峰值 RSS 由 GNU time 测量，不是同时运行的进程树内存之和；避免直接 wait4 把 Python 数据生成器的 fork 前堆算入目标程序。
- 机器并非专用于基准：1 分钟负载从约 2.31 升至 11.58，**尾延迟波动明显**。本次结果不是空闲 NAS 的稳定上限，也不应直接外推到百万/千万文件。

原始报告：[native-benchmark-100k.json](native-benchmark-100k.json)。

## 建库与更新

以下每种更新只有一次计时，不是统计分位数：

| 项目 | Rust | plocate |
|---|---:|---:|
| 首次建库（含 stats） | 5.87 s | 1.84 s |
| 无变更更新 | 0.118 s | 1.197 s |
| 一个目录内重命名（含 stats） | 1.424 s | 1.514 s |
| 建库峰值 RSS | 27.81 MiB | 147.73 MiB |
| 索引大小（不含 stats） | 17.82 MiB | 0.574 MiB |

无变更时原生引擎不改写 DB，也不重建统计缓存，因此优势明显。发生变化后统计刷新仍计入总耗时，不能从表中单独推断扫描耗时。

## 查询

单位 ms，未标明限量的查询返回全部匹配结果：

| 场景 | 命中数 | Rust P50 / P95 | plocate P50 / P95 |
|---|---:|---:|---:|
| 稀有关键词 | 1 | 13.37 / 85.61 | 16.09 / 73.49 |
| 普通关键词 | 25000 | 85.54 / 460.68 | 56.22 / 108.00 |
| 两关键词 AND | 25000 | 91.84 / 669.50 | 59.89 / 132.17 |
| 无匹配 | 0 | 7.27 / 12.93 | 15.75 / 24.27 |
| 两字节短关键词 | 25000 | 113.39 / 201.24 | 51.68 / 76.89 |
| glob | 25000 | 86.39 / 918.35 | 80.26 / 126.71 |
| 普通关键词，limit 50 | 50 | 13.99 / 45.44 | 20.48 / 109.51 |

本组查询的最大峰值 RSS：Rust 8.81 MiB，plocate 10.79 MiB。

## 结论与下一步

**当前版本不全面优于 plocate。** 原生引擎已经能独立完成建库、目录复用、候选检索和局部事务更新；无变更更新、无匹配和限量查询表现较好，建库峰值内存也较低。

但首次建库仍约慢 3.2 倍，索引约大 31 倍。大量结果、短词的吞吐及高负载下的尾延迟明显弱于 plocate，不能只展示少量结果查询的优势。

后续优化重点：

1. 将按目录分块的 posting 进一步合并/压缩，减少 SQLite B-tree 与碎片化页面访问。
2. 为短词提供独立候选结构，而不是扫描全部记录。
3. 把原生目录计数增量维护与统计缓存结合，避免单目录变化后遍历全库统计。
4. 增加真实路径分布、百万级数据及空闲/繁忙 NAS 的多轮重复测试。

## 复现

```bash
cargo build --release
python3 scripts/benchmark-native.py --files 100000 --runs 21 --warmup 3 \
  --output native-benchmark.json
```

对照测试需要 plocate、updatedb、plocate-build。只测试 Rust 加 `--native-only`。Python 3.8+ 为测试依赖，GNU time 为可选 RSS 测量工具；它们均不是原生引擎的运行依赖。
